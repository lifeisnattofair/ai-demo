# 기획 점검표 — 브레인스토밍에서 AI가 던진 질문

사업: (가상) 한빛아트센터 공연·교육 프로그램 통합 예약 플랫폼, 2026-11-23, superpowers:brainstorming
질문마다 **왜 물었나**(답이 바꾸는 것)와 **결정**을 함께 적었습니다. 다른 예약/결제 사업 기획에서도 점검표로 다시 쓸 수 있게 일반화한 질문을 덧붙였습니다.

| # | 영역 | AI가 던진 질문 | 왜 물었나 | 결정 | 일반화한 점검 질문 |
|---|---|---|---|---|---|
| 1 | 추진 배경 | 이 기관은 지금 무엇 때문에 불편해서 통합 예약 플랫폼을 발주하나요? | 신규 구축인지 교체인지, 데이터 이관/연계 요구사항이 필요한지가 갈린다 | 공연은 외부 예매처, 교육은 전화/구글폼으로 나뉘어 불편 → 신규 통합 구축 | 지금 업무는 어디서 어떻게 처리되고, 무엇이 흩어져 있는가? |
| 2 | 사업 범위 | 외부 예매처를 전면 대체, 병행, 단계적 대체 중 어떻게 할까요? | 병행하면 좌석 이중 판매 방지 연계가 핵심 난제가 된다 | 단계적 대체: 1차는 교육 + 자체 기획공연, 대관공연은 2차 | 기존 시스템과 공존하는 기간에 같은 자원을 두 곳에서 팔게 되지 않는가? |
| 3 | 사용자 역할 | 예약에 회원 가입이 필요한가요? | 1인 한도/할인 증빙/개인정보 범위가 모두 이 결정에 달려 있다 | 회원 전용, 관리자는 운영 담당/정산 담당 | 한도/중복 방지를 무엇(계정, 전화번호, 기기) 기준으로 지킬 것인가? 관리자 업무는 몇 역할로 나뉘는가? |
| 4 | 환불 정책 | 교육은 하루짜리 체험인가요, 여러 회차를 듣는 정규 강좌도 있나요? | 판매 단위(회차/과정)와 개강 후 중도 환불 계산 로직이 달라진다 | 둘 다 있음 → 정규 강좌는 과정 단위, 평생교육 반환 기준 준용 | 상품마다 판매 단위가 같은가? 이용이 시작된 뒤의 취소는 어떻게 처리하나? |
| 5 | 대기 정책 | 대기 승격 결제 기한은 적절한가요? 정규 강좌는 개강 후 추가 모집을 하나요? | 자동 결제(빌링키)를 쓰면 범위가 커진다. 승격 기한과 대기 유지 기간을 정해야 한다 | 승격 후 24시간 내 결제, D-2 이내는 일반 판매, 개강 후 추가 모집 없음 | 빈자리가 생기면 누구에게 언제까지 기회를 주고, 언제 일반 판매로 돌리나? |
| 6 | 범위 밖 | 범위 밖 목록에서 빼거나 더할 것이 있나요? | 프로토타입이 대체하는 방식(모의 인증, 알림함 등)을 명시해야 검수 기준이 흔들리지 않는다 | 제안 목록 그대로 채택 | 이번에 하지 않는 것과 그 대신 보여 주는 것을 문서에 적었나? |
| 7 | 완료 조건 | 검수 기준 9개에서 빠진 항목이 있나요? 꼭 보여 주고 싶은 검수 장면은? | 검수 기준이 곧 QA 문서와 브라우저 검수 항목이 된다 | 제안 9개 그대로 채택 | 정책 하나마다 「이렇게 되면 통과」를 확인할 장면이 있는가? |
| 8 | 구현 방식 | 데이터 저장소를 어디에 둘까요? (Netlify Blobs / Supabase) | 동시 결제 검증 방법과 데이터 산출물 형식(테이블 정의서)이 달라진다 | Netlify 한도 문제로 GitHub Pages + Supabase | 무료/제한된 인프라에서 꼭 증명해야 할 것(동시성, 키 보호)이 증명되는가? |

## AI가 먼저 제안하고 사용자가 수정 없이 채택한 정책

| 정책 | 제안 근거 |
|---|---|
| 공연 수수료(8일 전 무료, D-7~D-4 10%, D-3~D-1 30%, 당일 불가) | 사용자가 준 구간(D-7, D-3, 당일)을 흔한 예매처 수준으로 구체화 |
| 할인 증빙은 현장 확인, 파일 업로드 없음 | 장애 여부는 개인정보보호법상 민감정보 → 수집하지 않아 보안 범위 축소 |
| 1인 한도(공연 4매, 체험 4명, 정규 강좌 1건) | 정원제와 지정석의 성격 차이 |
| 선점 10분, 승인 직전 재검증 후 실패 시 즉시 결제 취소 | 결제 중 이탈/동시 결제 대응 |
| 좌석은 소공연장 약 200석 지정석, 웹 접근성 KWCAG 2.2 | 공공사업 필수 품질 항목 |
| 성능 목표는 적되 프로토타입에서는 동시성 정합성만 실측 | 문서 형식과 시연 가능한 범위 구분 |
| 화면 기술은 Next.js, React, Tailwind 대신 Vite + 바닐라 JS + KRDS | 사용자 요청: AI 기본 조합 대신 공공 맥락에 맞는 기술 검토 |

## 설계 검토(builder check)에서 나온 질문

문서를 쓴 뒤, 대화 맥락이 없는 별도 검토 에이전트에게 「이 문서만 보고 계획을 세울 수 있나」를 점검하게 했습니다.

| # | 검토자 질문 | 왜 중요한가 | 처리 | 일반화한 점검 질문 |
|---|---|---|---|---|
| 9 | 대기 승격 때 취소분이 신청 수량보다 적으면? 공연은 그 좌석을 묶나, 수량만 떼어 두나? | 대기 데이터 모델과 잔여석 계산식, 중복 판매 방지 로직이 갈린다 | 사용자 확정: 매수 지정, 건너뛰지 않고 모음, 취소 좌석 그대로 배정 | 「빈자리 1개」의 단위(좌석, 인원, 건)가 신청 단위와 맞는가? |
| 10 | 기한이 D-2 안으로 넘어가 만료되면? | 정책 두 개(24시간, D-2)가 겹치는 경계 | 사용자 확정: 일반 판매로 전환 | 두 정책의 기한이 겹칠 때 어느 쪽이 이기는가? |
| 11 | 정규 강좌 경과 비율은 기간인가 회차인가? 정확히 1/3이면? | 환불 기대값과 테스트 케이스가 직접 바뀐다 | AI 판단: 시작한 회차 수 기준, 「전」은 미만 | 비율 정책의 분모와 경계값을 숫자 예시로 적었나? |
| 12 | 공개 시연 때 메일 발송/관리자 계정/일시 정지는? | 인증 설정과 시드/초기화 기능, 시연 안내가 정해진다 | 사용자 확정: 이메일 확인 끔, 관리자 계정 공개, 초기화 기능 | 외부인이 직접 써 볼 때 막히는 지점(메일, 권한, 데이터 오염)은? |
| 13 | 검수용 시계를 공개본에서 켜면 모든 열람자에게 영향이 가지 않나? | 환경 분리와 배포 구성이 달라진다 | 사용자 확정: 프로젝트 2개로 분리 | 테스트용 장치가 실제 이용자에게 새어 나가지 않는가? |
| 14 | 원 미만은 수수료에서 버리나, 환불액에서 버리나? | 1원 차이도 「환불액 불일치」 실패가 된다 | AI 판단: 환불액에서 버림 | 반올림 위치를 예시 금액으로 적었나? |
| 15 | 할인은 몇 매까지, 교육 상품에도 적용하나? | 할인 계산 함수와 화면 선택 제약이 바뀐다 | AI 판단: 다자녀 전 매수, 장애인/유공자 본인 + 동반 1, 정규 강좌는 본인만 | 할인마다 적용 대상과 매수 상한이 정해져 있나? |
