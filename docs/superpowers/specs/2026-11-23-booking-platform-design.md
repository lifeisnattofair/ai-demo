# 설계 문서 — 문화예술회관 통합 예약 플랫폼 (프로토타입)

**작성일**: 2026-11-23, **상태**: 승인 (2026-11-23)
**요구사항**: [요구사항정의서](2026-11-23-booking-platform-requirements.md) (요구사항 64개, ID는 그 문서 기준)
**질문 기록**: [기획 점검표](../notes/planning-checklist.md)

## 1. 의도와 이유

- **무엇**: 가상 공공사업 「한빛아트센터 공연·교육 프로그램 통합 예약 플랫폼」의 작동하는 프로토타입입니다.
- **왜**: 공공/문화기관 웹 플랫폼 기획자의 포트폴리오에 들어갈 결과물입니다. 「요구사항 정의 → 구현 계획(추적표) → 테스트 우선 구현 → QA/브라우저 검수 → 리뷰 → 산출물 정리」 흐름을 실물과 단계별 산출물로 보여 줍니다. 그래서 보기 좋은 화면보다 **공공 사업 문서 형식과 정책 규칙이 실제로 지켜지는 것**이 더 중요합니다.
- **누가 보나**: 포트폴리오 열람자(공공 SI/기관 실무자)입니다. 캡처와 문서로 보는 사람이 대부분이고, 일부는 직접 시연해 봅니다.

## 2. 목표, 비목표, 실패 조건

- **목표**
  - 요구사항정의서의 검수 기준 AC-1~AC-9를 모두 충족합니다.
  - 정책 규칙(수수료, 중도 환불, 선점, 대기, 한도, 할인)이 테스트로 증명됩니다.
  - 단계별 산출물과 캡처를 `portfolio/`에 남깁니다.
- **비목표**: 실운영 수준의 성능/가용성, 실제 결제와 정산, 대관공연. 전체 범위 밖 목록은 요구사항정의서 Ⅴ장에 있습니다.
- **실패 조건**: 겉으로는 동작해도 아래 가운데 하나라도 해당하면 실패로 봅니다.
  - 같은 좌석이 두 번 팔린다.
  - 환불액이 정책 표와 다르다.
  - 결제 키가 저장소나 브라우저 코드에 노출된다.
  - 키보드로 예약을 끝낼 수 없다.
  - 실제 기관이나 실제 개인정보처럼 보이는 데이터가 들어간다.

## 3. 제약

- 결제는 토스페이먼츠 **테스트 모드**만 씁니다. 테스트 키와 공개 테스트 카드만 사용하고, 키는 환경 변수로만 다룹니다(COR-002, COR-003).
- 호스팅은 **GitHub Pages(정적) + Supabase 무료 플랜**입니다(COR-004). Netlify 무료 한도가 부족해서 바꿨습니다.
  - GitHub 무료 계정에서 Pages를 쓰려면 저장소를 공개해야 합니다. 공개와 배포는 사용자가 요청할 때만 합니다.
- git 작성자는 `lifeisnattofair`입니다. 저장소 로컬 설정에만 적용했습니다.

## 4. 검토한 방식 (Approaches)

| 안 | 구성 | 장단점 | 결과 |
|---|---|---|---|
| A | Netlify Functions + Netlify Blobs | 계정 하나로 끝납니다. 키-값 저장소라 정산 집계는 코드로 하고, 테이블 정의서 형식과 결이 다릅니다. | 제외 |
| B | Netlify Functions + Supabase(Postgres) | DB 고유 제약으로 중복 판매를 막고, 정산은 SQL 집계로 처리합니다. 테이블 정의서를 만들 수 있습니다. | 처음 추천안 |
| B′ | **GitHub Pages + Supabase(DB, 인증, Edge Functions)** | B의 장점을 유지하면서 Netlify 한도를 쓰지 않습니다. 대신 서버 함수가 Deno 런타임이고, 저장소를 공개해야 합니다. | **사용자 선택** |
| C | 브라우저 저장소 + 결제 함수만 | 사용자끼리 상태를 공유하지 못해 동시 결제/대기 승격을 시연할 수 없습니다. | 제외 |
| — | GitHub Pages + Cloudflare Workers | 무료 한도는 넉넉하지만 DB를 따로 골라야 해서 계정이 하나 더 늘어납니다. | 제외 |

### 기술 스택 판단 (AI 기본값 대신 공공 맥락 기준)

사용자 요청: 「AI 기본 조합(Next.js, React, Tailwind, PostgreSQL)이 최적이 아니라면 공공 서비스 특성에 맞는 쪽을 고려해 달라.」

| 영역 | 흔한 AI 기본값 | 이번 선택 | 이유 |
|---|---|---|---|
| 화면 | Next.js + React | **Vite + 바닐라 JavaScript(ES 모듈)** | 서버 렌더링이 필요 없는 정적 배포(GitHub Pages)입니다. 공공 SI 퍼블리싱 산출물이 HTML, CSS, JS 기반이라, 화면 산출물을 그대로 보여 주기 쉽습니다. |
| 스타일 | Tailwind | **KRDS(대한민국 정부 디자인 시스템) 공식 HTML 컴포넌트 키트 + 디자인 토큰, Pretendard GOV** | 공공 웹/앱 UI/UX 가이드라인의 기준 디자인 시스템이고, KWCAG 2.2를 따르도록 설계됐습니다. 토큰은 원본을 고치지 않고 프로젝트 CSS에서 다시 선언합니다. |
| DB | PostgreSQL | **PostgreSQL (Supabase)** | MariaDB를 우선 검토했습니다. 하지만 무료 호스팅과 서버 함수/인증을 함께 제공하는 선택지가 마땅치 않았습니다. PostgreSQL도 공공에서 쓰이는 공개SW DBMS입니다(정부 클라우드 센터의 멀티 DBMS 채택 사례). 이식성을 위해 표준 SQL 위주로 작성합니다. |
| 서버 | Next.js API | **Supabase Edge Functions** | 결제 승인, 취소, 웹훅에만 씁니다. 결제 비밀 키는 함수 환경 변수에 둡니다. |

**실사업 전환 대응표** (COR-006, 포트폴리오에서 「실제 발주라면」으로 설명할 부분)

| 프로토타입 | 실사업 권장 |
|---|---|
| Vite + 바닐라 JS + KRDS | 전자정부 표준프레임워크 화면 계층(JSP/Thymeleaf 또는 별도 프런트) + KRDS |
| Supabase Edge Functions | 전자정부 표준프레임워크(Spring) 서비스 계층 |
| PostgreSQL 함수(트랜잭션 처리) | 서비스 계층 트랜잭션 + MariaDB / Tibero / PostgreSQL |
| Supabase Auth + 모의 본인인증 | 기관 회원 시스템 + 본인확인기관 연동 |
| 화면 내 알림함 | 문자/알림톡 발송 대행 연계 |

## 5. 정해진 설계

### 5-1. 구성도
```
[브라우저]  GitHub Pages (Vite 빌드 정적 파일, KRDS)
   │  ① 조회, 선점, 대기 등: Supabase 클라이언트(anon key) + 행 단위 접근 정책(RLS) + DB 함수(RPC)
   │  ② 결제: 토스 결제위젯(테스트 클라이언트 키) → successUrl 복귀
   ▼
[Supabase]
   ├─ Auth (이메일 가입/로그인, 역할: member / operator / finance)
   ├─ PostgreSQL (테이블 + 고유 제약 + 트랜잭션 함수)
   └─ Edge Functions
        ├─ payments-confirm  : 금액 재계산 → 선점 재검증 → 토스 승인 → 확정 / 실패 시 토스 취소
        ├─ payments-cancel   : 환불액 계산 → 토스 취소(부분) → 환불 기록 → 대기 승격 처리
        └─ payments-webhook  : 토스 조회 API로 재확인 → 멱등 반영
[토스페이먼츠 테스트 환경]
```

### 5-2. 정책 로직 분리
- 수수료 구간, 중도 환불 비율, 선점 만료, 대기 승격 대상/기한, 1인 한도, 할인 금액 계산은 **저장소와 무관한 순수 함수 모듈**로 만듭니다.
  - 입력: 금액, 일시, 현재 시각.
  - 출력: 결과값.
- 이 모듈을 TDD(Vitest)로 먼저 작성합니다(QUR-005). 화면(금액 미리보기)과 Edge Functions(최종 계산)가 **같은 모듈**을 씁니다.
- 현재 시각은 항상 인자로 받습니다. 검수용 시계(SFR-025)는 DB의 `app_clock` 오프셋 값으로 구현하고, 검수 환경 플래그가 켜졌을 때만 적용합니다.

### 5-3. 중복 판매 방지 (PER-004, AC-3)
- **좌석**: 회차별 좌석 상태 행에 `(회차, 좌석)` 고유 제약을 둡니다. 선점은 DB 함수 안에서 한 트랜잭션으로 처리합니다. 만료된 선점을 정리한 뒤 삽입하고, 충돌하면 실패합니다.
- **정원제(체험/정규 강좌)**: 회차 행을 잠근 상태에서 「확정 수 + 유효 선점 수 ≤ 정원」을 확인한 뒤 선점합니다.
- **확정**: `payments-confirm`이 토스 승인 **전에** 선점을 「결제 중」으로 표시합니다. 승인 후에는 확정 처리를 원자적으로 합니다. 선점이 만료됐거나 다른 사람이 먼저 확정했으면 토스 취소 API로 즉시 전액 취소하고, 사용자에게 사유를 알립니다.
- **선점 만료**: 별도 스케줄러 없이 **조회/선점 시점에 만료 시각과 비교**해 처리합니다(지연 만료). 그래서 검수용 시계로 결과를 확실하게 재현할 수 있습니다.

### 5-4. 대기 승격
- 대상: 공연 회차, 체험 회차, 정규 강좌 과정. 매진일 때만 대기를 신청할 수 있습니다.
- **수량** *(사용자 확정)*
  - 대기 신청 때 매수(인원)를 받습니다. 1인 한도 안에서 받고, 정규 강좌는 1명입니다.
  - 취소분은 순번대로 모읍니다. 1순위가 신청한 수량만큼 모이면 1순위를 승격합니다. 모자라면 **건너뛰지 않고** 다음 취소분을 기다립니다.
  - 남는 수량은 2순위 몫으로 이어서 모읍니다.
- **공연 좌석** *(사용자 확정)*
  - 취소된 **바로 그 좌석**을 승격자에게 배정합니다. 승격자가 좌석을 다시 고르지 않습니다.
  - 모으는 동안과 승격 기한 동안 그 좌석은 「대기 배정」 상태입니다. 선점과 같은 좌석 상태 행을 쓰므로 5-3의 중복 방지 규칙이 그대로 적용됩니다.
- **기한**
  - 승격 시 결제 기한은 24시간입니다.
  - 기준일 D-2 이내에 일어난 취소분은 승격하지 않고 일반 판매로 풉니다.
  - 결제 기한이 D-2 안으로 넘어가 만료되면 다음 순위로 넘기지 않고 일반 판매로 풉니다. *(사용자 확정)*
  - 모으던 수량이 D-2 시점까지 다 차지 못해도 일반 판매로 풉니다.
- 만료는 지연 처리합니다. 다음 조회 시점이나 관리자 화면을 열 때 처리합니다.

### 5-5. 금액/시간 규칙
- 금액은 원 단위 정수입니다. 할인 후 결제액을 먼저 정합니다. 할인액은 매수별로 계산해 원 미만을 버립니다.
- **환불액 = floor(결제액 × 환불 비율)**, **수수료 = 결제액 − 환불액**입니다. 원 미만은 환불액에서 버립니다(DAR-003). 예: 12,345원, D-7 구간이면 환불 11,110원, 수수료 1,235원. *(빌더 점검 후 AI 판단)*
- D-day는 KST 달력 날짜 차이로 계산합니다(DAR-004). 예: 관람일 12/10, 취소 12/3이면 D-7이므로 수수료 10%.
- **정규 강좌 경과 비율** *(빌더 점검 후 AI 판단)*
  - 계산식은 「취소 시각 이전에 **시작 시각이 지난** 회차 수 ÷ 총 회차 수」입니다. 회차 수 기준이라 시연할 때 설명하기 쉽습니다.
  - 경계값은 「전」을 미만으로 봅니다. 12회 중 4회가 지나 정확히 1/3이면 「1/3 경과 전」이 아니므로 1/2 환불입니다. 6회가 지나 정확히 1/2이면 환불하지 않습니다.
  - 첫 회차 시작 전에는 개강 전 수수료 표를 적용합니다. 그래서 개강 당일(D-0)에는 첫 회차 시작 전이라도 취소할 수 없습니다(공연과 같은 규칙).
- **할인 적용 범위** *(빌더 점검 후 AI 판단)*
  - 장애인/국가유공자: 본인 1매 + 동반 1매까지 50%입니다.
  - 다자녀: 한 예약의 전 매수(한도 4매 안)에 30%입니다.
  - 할인은 중복 적용하지 않고, 매수별로 하나만 고릅니다.
  - 체험에도 같은 체계를 씁니다. 정규 강좌는 본인 1건이라 동반 할인 없이 본인 할인만 적용합니다.

### 5-6. 화면 목록
- **사용자 화면**
  - 프로그램 목록, 프로그램 상세/회차
  - 좌석 선택(배치도 + 목록 대체), 인원/과정 신청
  - 할인/결제 확인, 결제 성공/실패
  - 내 예약 목록/상세(취소)
  - 대기 현황, 알림함, 로그인, 가입, 회원 정보
- **관리자 화면**
  - 대시보드
  - 프로그램 목록/편집, 회차/좌석 편집
  - 예약 내역, 대기자, 결제/환불 내역, 회차 취소 승인
  - 정산 현황, 작업 이력, 검수용 시계(검수 환경만), 시연 데이터 초기화(공개 시연 환경만)

### 5-7. 환경 구성 *(사용자 확정)*
| 환경 | Supabase 프로젝트 | 검수용 시계 | 용도 |
|---|---|---|---|
| 로컬 개발 | 로컬(Supabase CLI) 또는 검수용 프로젝트 | 켬 | TDD, 동시성 통합 테스트 |
| 검수 | 검수용 프로젝트 | 켬 | AC-2, 4, 5 재현, QA 캡처 |
| 공개 시연 | 시연용 프로젝트 | **끔**(플래그로 비활성, 관리자 메뉴에 노출 안 됨) | 포트폴리오 열람자 시연 |

- 화면 빌드는 환경 변수로 연결할 프로젝트와 시계 사용 여부를 정합니다. SFR-025의 「운영 환경 비활성」은 시연용 빌드에서 시계 메뉴가 없고, DB 함수가 오프셋을 무시하는 것으로 증명합니다.
- **시연용 인증**: 가입 때 이메일 확인을 끕니다. 무료 플랜 기본 메일은 외부 주소로 가지 않기 때문입니다. 비밀번호 재설정은 검수 환경의 팀원 메일로만 검수합니다.
- **관리자 시연 계정**: 운영 담당/정산 담당 계정을 README에 공개합니다. 「시연 데이터 초기화」(SFR-026)로 시드 상태로 되돌립니다.
  - 초기화는 운영 담당 시연 계정에서 실행합니다. 토스 테스트 거래는 남아도 괜찮습니다.
- 무료 프로젝트는 오래 쓰지 않으면 일시 정지될 수 있습니다. 이 점을 README 시연 안내에 적습니다.

### 5-9. 디자인 콘셉트 *(2026-11-23 사용자 확정)*

공통 기준은 두 가지입니다. KRDS 컴포넌트 구조와 접근성 규칙은 그대로 따르고, 토큰은 프로젝트 CSS에서 다시 선언해 조정합니다.

**사용자 화면: 「포스터가 색을 맡고, UI는 물러난다」**
- **목표**: 공연 포스터로 다채롭게 보이게 하되, 예약 과정은 깔끔하고 직관적이어야 합니다.
- **색**
  - UI는 무채색(흰 바탕, 진한 글자, 가는 선)으로 둡니다. 화면에서 색은 포스터 이미지와 행동 버튼에만 나옵니다.
  - 예약/결제 같은 행동 버튼은 **KRDS 대표 색 하나**로 통일합니다. 사용자가 「누를 수 있는 것은 이 색」으로 알아보게 하려는 것입니다.
  - 상품 유형(공연, 체험, 정규 강좌)은 작은 색 라벨로 구분합니다.
- **목록/상세**
  - 목록은 포스터 비율(세로형) 카드 격자로 구성합니다.
  - 상세는 큰 포스터와 편집형 타이포그래피를 쓴, 도록 같은 화면입니다.
- **예약 단계(회차 → 좌석/인원 → 할인 → 결제 → 완료)**
  - 장식을 빼고 단계 표시기, 선택 요약, 남은 선점 시간을 고정 영역에 둡니다.
  - 한 화면에서 결정은 하나만 하게 합니다.
- **포스터 이미지** *(사용자 지시로 변경)*
  - 실제 공연 포스터는 저작권 때문에 쓰지 않습니다.
  - 도형을 조합한 SVG 포스터는 쓰지 않습니다. 대신 **무료 사진(상업적 이용 가능 라이선스)** 위에 프로그램별 타이포그래피를 얹어 포스터를 디자인합니다.
  - 알맞은 무료 사진이 없으면 이미지 생성 서비스로 만듭니다. 사용자가 직접 생성해 줄 수도 있습니다.
  - 사진은 저장소에 내려받아 두고, 출처와 라이선스는 `src/assets/images/CREDITS.md`에 기록합니다. 사진을 내려받을 때마다 사용자 확인을 받습니다.

**시안, 화면 품질 기준** *(사용자 지시, 시안과 프로토타입 모두 적용)*
- 완성 전 프로토타입처럼 보이면 안 됩니다. 바로 출시할 수 있는 수준의 디자인과 완성도를 갖춥니다.
- 실제 사이트처럼 보여야 합니다. 「목업 데이터입니다」 같은 설명 문구나 설명용 UI는 넣지 않습니다.
- 디자인 요소는 선과 도형을 그냥 조합하지 않습니다. 요소마다 특성, 용도, 가독성, 심미성을 따져 만듭니다.
- 시안은 반응형 HTML로 만듭니다(PC 1440, 모바일 390).
- **금지**: 도형이나 카드 옆에 포인트 색 두꺼운 선(좌측 강조 막대 등)을 두지 않습니다. AI 티가 나고 시선이 흩어지기 때문입니다.
- 가운뎃점(·)은 꼭 필요한 곳에만 씁니다.

## 7. 검토자 점검 결과와 처리

별도 검토 에이전트가 「이 문서만 보고 계획을 세울 수 있나」를 점검하고 질문 6개를 냈습니다.

| # | 질문 | 처리 |
|---|---|---|
| 1 | 대기 승격 수량, 부족분 처리, 좌석 묶음 방식, D-2 경계 만료 | 사용자 확정 → 5-4 |
| 2 | 정규 강좌 경과 비율 기준과 경계값(정확히 1/3, 개강 당일) | AI 판단 → 5-5 |
| 3 | 공개 시연 환경(메일 발송, 관리자 계정 공개, 일시 정지) | 사용자 확정 → 5-7 |
| 4 | 검수 환경과 운영 환경 분리(전역 시계 충돌) | 사용자 확정 → 5-7 |
| 5 | 원 미만 처리 위치(수수료 쪽인가 환불액 쪽인가) | AI 판단 → 5-5, DAR-003 |
| 6 | 할인 유형별 적용 매수, 교육 상품 적용 | AI 판단 → 5-5 |

**AI 판단으로 정한 것** (승인 때 확인할 항목)
- 환불액은 원 미만을 버리고, 수수료는 「결제액 − 환불액」입니다.
- 경과 비율은 「시작한 회차 수 ÷ 총 회차 수」입니다. 「전」은 미만으로 봅니다.
- 개강 당일에는 취소할 수 없습니다.
- 다자녀 할인은 전 매수에, 장애인/유공자 할인은 본인과 동반 1인에게 적용합니다. 정규 강좌는 본인 할인만 있습니다.
- 예약 부분 취소는 범위 밖입니다.
- 선점/대기 기한 만료는 스케줄러 없이 지연 처리합니다.
- 화면 기술은 Vite + 바닐라 JS + KRDS입니다.
