# 최종 정리 - (가상) 한빛아트센터 공연·교육 프로그램 통합 예약 플랫폼 구축

## 한 단락 요약

공연은 외부 예매처, 교육은 전화와 구글폼으로 따로 받던 가상의 문화예술회관을 하나의 회원 예약 플랫폼으로 묶는 공공사업을 처음부터 끝까지 진행했다. 공공 RFP 형식의 요구사항정의서(요구사항 64개, 검수 기준 9개)로 시작해 요구사항 추적표가 붙은 구현 계획, 디자인 콘셉트와 출시 수준 시안, 테스트 우선 방식의 프로토타입(사용자 화면 14개, 관리자 화면 11개, DB 마이그레이션 17개), QA 케이스 88건의 검수, 공공 양식 산출물 7종까지 만들었다. 기획자인 내가 범위와 정책, 화면 기준을 정하고, AI 에이전트들이 구현, 리뷰, QA 실행을 나눠 맡는 방식으로 진행했다.

## 배경

- 공공기관과 문화예술 기관의 서비스 기획을 해 오며, 실제 사업에서 가장 많이 어긋나는 곳이 요구사항과 결과물 사이라는 것을 봤다. 요구사항이 화면과 테스트, 검수까지 끊기지 않고 이어지는 과정을 AI와 함께 어디까지 만들 수 있는지 보여 주고 싶었다.
- 그래서 실제 발주처 RFP나 개인정보는 쓰지 않고, 공개된 양식 구조만 참고한 가상의 사업으로 정했다. 범위는 문화예술회관에서 흔한 문제(공연 예매처와 교육 접수 창구가 따로임)로 잡았다.
- 기술은 AI가 기본으로 고르기 쉬운 Next.js, React, Tailwind 대신 공공 서비스 맥락에 맞게 바닐라 JavaScript와 KRDS(범정부 디자인 시스템) 토큰, PostgreSQL을 택했다. 실제 발주 시 전자정부 표준프레임워크와 국산/공개 DBMS로 옮기는 전환표도 요구사항에 넣었다.

## 핵심 포인트 4개

1. **요구사항이 끝까지 이어진다.** 요구사항 64개가 구현 Task, 자동 테스트, QA 케이스 88건, 검수 결과까지 추적표 한 장에서 연결된다. 누락은 점검 스크립트(`check:trace`)가 빌드 때마다 잡고, 추적표의 진행 상태는 QA 결과에서 자동으로 채운다.
2. **돈과 시간 규칙을 DB에서 지킨다.** 좌석 10분 선점, 1인 한도(공연 4매, 체험 4명, 강좌 1명), 취소 시점별 환불(원 미만 버림), 대기 24시간 결제 기한, 공연 2일 전 일반 판매 전환을 모두 DB 함수와 테스트로 고정했다. 같은 좌석 동시 결제는 1건만 확정되고 나머지는 자동 취소된다(DB 테스트 180건).
3. **공공 서비스 품질 기준을 화면에 적용했다.** KRDS 토큰, 키보드만으로 좌석 선택, 접근성 자동 점검 32개 화면 위반 0, 개인정보 가림과 역할별 메뉴, 모든 화면의 로딩/빈/오류 상태. 「AI 같은 화면」을 피하려고 anti-slop 감사(27건 수정)와 출시 점검(102회 측정, FAIL 0)을 거쳤다.
4. **AI를 팀처럼 나눠 쓰고, 서로 검증하게 했다.** 구현 에이전트, 리뷰 에이전트, QA 에이전트를 분리하고, 계획과 다르게 판단한 곳 23군데는 「무엇을, 왜, 틀리면 비용」으로 기록했다. 리뷰를 통과한 코드에서 QA가 「대기 신청 화면 누락」을 찾았고, 그 수정분을 다시 리뷰해 2차 결함 3건을 더 찾았다.

## 어려웠던 점

가장 크게 배운 것은 리뷰와 QA가 서로를 대신하지 못한다는 점이다. Task마다 코드 리뷰를 받고 마지막에 가장 강한 모델로 전체 리뷰까지 통과했는데도, 매진 회차의 「대기 신청」 버튼이 막다른 화면으로 이어진다는 사실은 요구사항을 들고 화면을 끝까지 따라간 QA에서야 드러났다. 서버 함수와 테스트는 있었지만 화면이 그 함수를 부르지 않았고, 코드만 보는 리뷰는 「없는 호출」을 찾기 어려웠다. 환경 문제도 컸다. Windows의 Docker Desktop이 E: 드라이브를 컨테이너에 보여 주지 않아 결제 서버 함수가 모두 부팅 오류로 끝났고, 원인을 찾은 뒤 함수를 임시 폴더로 복사해 띄우는 도우미를 만들었다. 동시 결제와 회차 취소가 겹칠 때의 DB 교착은 잠금 순서를 하나로 정하고 동시 요청 테스트로 고정해 해결했다. 대기 기한이 「다른 회원이 움직여야」 만료되던 문제는 매분 도는 DB 예약 작업으로 바꿨는데, 이번에는 그 작업이 시간을 옮기는 테스트를 흔들어 테스트 동안 작업을 멈추는 장치를 더했다.

## 시연 방법

실제 배포는 하지 않았고, 로컬에서 시연한다(README의 「로컬 실행」).

1. `npx supabase start` → `.env` 작성 → `npm run dev`(사용자 화면 `http://localhost:5173`, 관리자 `/admin.html`) → 다른 터미널에서 `npm run functions:serve`(모의 결제)
2. 관리자 화면에 운영 담당(operator@demo.test)으로 들어가 「시스템 > 시연 데이터 초기화」를 실행해 처음 상태로 맞춘다. 시연 계정 비밀번호는 모두 `Demo-1234!`
3. 5분 시나리오
   - 회원(member1@demo.test): 「현의 대화」 → 좌석 2석(키보드로도 가능) → 장애인 + 동반 할인 → 모의 결제 → 내 예약 → 취소 미리보기(수수료 구간)
   - 관리자 운영 담당: 「검수용 시계 +7일」로 취소 구간이 바뀌는 것 보여 주기 → 회차 등록 후 사용자 화면에 바로 반영
   - 매진과 대기: 정원이 찬 회차에서 다른 회원이 「대기 신청」 → 앞 회원 취소 → 승격 알림과 24시간 결제 기한 → 「검수용 시계 +1일」 후 만료 처리
   - 관리자 정산 담당(finance@demo.test): 정산 현황에서 순매출 = 결제 - 환불, CSV 내려받기, 작업 이력
4. 산출물은 `deliverables/`(요구사항정의서, 기획 점검표, 요구사항 추적표, 테이블/코드 정의서, 화면 설계서, 테스트 결과서), 캡처는 `portfolio/shots/`
